# 产品发现验证闭环

当发现任务已有多个方案方向、关键价值仍依赖高风险假设，或需要支持继续、暂停、转向和优先级决定时，使用本协议。目标是把产品发现推进到可验证、可更新决定的状态。

## 一、建立验证起点

先确认以下内容：

- 目标结果：谁在什么场景下需要发生什么可观察变化。
- 当前决定：这轮验证要支持继续、暂停、转向、淘汰还是排序。
- 已有证据：用户行为、业务数据、访谈、现状流程、历史实验或可信研究。
- 真实约束：合规、安全、合同、时间、资源和组织责任。
- 当前假设：缺少证据且错误时会影响产品选择的判断。

无法说清目标结果和当前决定时，先回到发现问题定义；已有明确决定且不存在高风险未知项时，直接进入下游。

## 二、形成候选方向

需要比较方案时，围绕同一目标考虑有实际价值的替代方向，例如：

- 保持现状、人工补偿或流程优化。
- 最小产品机制。
- 完整产品方案。

只保留能够解释“用户动作—产品机制—反馈—目标结果”因果链的方向。候选方向受已确认硬约束限制时可以减少数量，不为凑数制造无效方案。

## 三、识别风险假设

按实际场景从以下八类风险中选取相关项检查候选方向，不逐类强制展开：

| 风险类别 | 需要回答的问题 |
| --- | --- |
| 价值 | 目标用户是否真的需要，使用后是否产生预期结果 |
| 易用性 | 用户能否理解、完成任务并处理错误 |
| 商业可行性 | 成本、收益、服务和持续运营是否成立 |
| 技术可行性 | 现有数据、系统和能力能否支撑产品效果 |
| 伦理与合规 | 是否引入不当决策、隐私、合规或公平风险 |
| 推广采用 | 目标用户能否被触达、愿意尝试并完成迁移 |
| 战略协同 | 是否服务当前产品方向，是否挤占更高价值机会 |
| 团队交付 | 责任人、协作机制、资源和交付能力是否具备 |

将假设分为：

- 承重假设：一旦错误，会推翻方向、首期范围、关键机制或验收口径。
- 普通假设：错误后只需调整局部设计、表达或执行方式。

## 四、确定验证顺序

按以下因素排序：

1. 错误影响：错误时对价值、范围、风险和投入的影响。
2. 证据缺口：现有证据是否直接、近期且适用于当前场景。
3. 决定时点：最晚需要在何时确认。
4. 验证成本：获得有效证据需要的时间、资源和外部协调。
5. 可逆性：错误决定能否低成本撤回。

优先验证高影响、低证据、临近决定点且验证成本可控的假设。缺少可靠数据时使用高、中、低分级并说明依据，不生成伪精确分数。

## 五、设计最小验证

每个实验或验证动作至少包含：

| 项目 | 内容要求 |
| --- | --- |
| 待验证假设 | 一句可以被证据支持或否定的判断 |
| 目标对象 | 真实用户、业务角色、数据范围或流程节点 |
| 验证方法 | 访谈、行为观察、数据分析、原型测试、人工服务或小范围试运行 |
| 行为或结果指标 | 优先观察真实行为、业务结果和实际投入 |
| 通过阈值 | 达到什么条件可以继续当前方向 |
| 失败动作 | 未达到阈值时暂停、转向、缩小范围或补充证据 |
| 责任人与最晚确认点 | 谁执行、谁确认、何时必须形成结论 |
| 证据留存 | 原始数据、访谈记录、测试记录或评审结论的路径 |

无法获得真实行为证据时，可以先使用访谈或专家判断缩小范围，同时标明证据强度和下一步补证动作。

## 六、设置确认点

以下节点用于检查依据和记录当前判断，不自动触发暂停：

1. 目标结果和本轮决定已明确。
2. 候选方向已收敛。
3. 承重假设及验证顺序已形成。
4. 验证方法、阈值、责任人和最晚确认点已确定。

记录建议与依据后继续已授权工作。只有新增授权、不可推断且会阻断当前交付的关键选择，或真实业务审批需要有权角色确认时，暂停对应动作；不重复询问已明确的决定。

## 七、回写结果

验证完成后，将每项假设更新为待验证、已验证、被否定或已转为决定，并记录证据、适用范围和日期。被否定的假设保留结论，避免后续阶段重新引入。

发现阶段以“决定得到足够证据支持，或剩余不确定性已有责任人、阈值和最晚确认点”为完成条件。验证失败时调整受影响的方向并说明依据；可交付已成熟部分和带假设边界的 PRD，不把失败方向写成已确认需求。
