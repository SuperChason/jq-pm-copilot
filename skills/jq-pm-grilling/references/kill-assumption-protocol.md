# 承重假设检验协议

当用户要求找出致命假设、红队检验、压力测试关键主张、明确停止条件，或需要决定本周先验证什么时，使用本协议。目标是找出少数会真正推翻方案的判断，并给出最低成本的验证动作。

## 一、识别承重主张

从方案中提取关于用户、价值、机制、数据、约束、成本、风险、时间和协作的关键主张。满足以下任一条件时，将其视为承重主张：

- 错误后目标结果无法实现。
- 错误后首期范围或产品机制需要重构。
- 错误后合规、安全、数据或商业风险不可接受。
- 错误后当前投入顺序失去依据。
- 错误后验收口径无法成立。

局部文案、可逆界面细节和不影响决定的执行偏好不进入承重假设清单。

## 二、先还原最强成立条件

对每个承重主张先写清：

- 支持它的最强证据和适用范围。
- 需要同时成立的前提。
- 当前证据仍覆盖不到的部分。

基于主张的最强版本寻找薄弱点。材料已经充分支撑的判断明确保留，避免为了制造问题重复质疑。

## 三、形成可证伪表达

每个承重假设使用以下卡片：

| 项目 | 内容要求 |
| --- | --- |
| 关键主张 | 当前方案依赖什么判断 |
| 最强支持 | 现有证据、适用范围和可信度 |
| 失败条件 | 出现什么事实时该主张无法继续成立 |
| 本周证据 | 本周能够获得的具体数据、访谈、观察或验证记录 |
| 停止或转向阈值 | 达到什么条件必须暂停、缩小范围或更换方案 |
| 最低成本验证 | 最小范围、最短路径且足以改变当前判断的动作 |
| 决定影响 | 验证结果会改变哪个方向、范围、规则或验收结论 |
| 责任人与期限 | 谁执行、谁确认、何时形成结论 |

失败条件必须具体、可观察。无法定义失败条件时，说明当前主张仍过于抽象，先回到目标结果或因果链拆解。

## 四、确定检验顺序

按以下因素排序：

1. 错误影响。
2. 当前证据下错误的可能性。
3. 验证所需时间和成本。
4. 决定的可逆性与最晚确认点。

优先处理高影响、证据薄弱、验证成本低且临近决定点的假设。最终保留三到五项；只有一项真正承重时如实保留一项。

## 五、在逐题拷问中使用

逐题模式先在内部形成排序，每轮只向用户处理最高优先级的一项：

1. 说明当前承重主张及其最强支持。
2. 提出一个会改变该主张的关键问题。
3. 给出推荐判断、替代方向和主要取舍。
4. 用户确认后记录失败条件、阈值和最低成本验证。
5. 更新决定或假设状态，再进入下一项。

用户明确要求一次性报告时，输出排序后的承重假设卡，同时列出“已有充分支撑的判断”和“当前无法评估的缺口”。

## 六、停止条件

满足以下条件后停止继续攻击：

- 承重主张已有直接证据或明确验证计划。
- 每项都有失败条件、停止或转向阈值、责任人和最晚确认点。
- 剩余问题只影响局部执行，不再改变方向、范围、重大风险或验收。

检验结果进入工作假设或决定记录。已经被证据否定的主张保留原因和影响，防止后续阶段再次作为前提使用。
