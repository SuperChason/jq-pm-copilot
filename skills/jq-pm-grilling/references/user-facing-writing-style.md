# 面向用户的表达协议

## 默认方式：轻度整理

面向用户的回复、说明、建议、评审意见和正式交付稿，默认采用“轻度整理”：

- 保留用户原本要表达的意思、事情发生的顺序、真实动作和不确定感。
- 删除口头禅、无意义重复和影响阅读的断句，补足必要的主语与连接关系。
- 先把具体场景、项目事实和实际问题讲清，再提炼判断、方法或结构。
- 用户的原话已经准确时，优先沿用原话中的词，不为了显得专业而替换成更抽象的概念。
- 正式材料可以有清楚的结构，但正文仍要直接、自然、具体，读起来像一个了解项目的人在说话。

轻度整理不是逐字转写。可以调整句序、合并重复内容、修正明显口误，但不能为了句式整齐改变原意，也不能删掉对理解过程有帮助的犹豫、失败、转折和限制条件。

## 项目内容先下钻

遇到项目方案、业务场景、产品设计和 AI 能力设计时，先研究材料，再写观点：

1. 从项目资料中找出具体场景、业务对象、角色、流程、规则、字段、指标、数据字典、系统关系和已有决定。
2. 把材料能够直接证明的内容、根据材料推出来的判断、当前还缺证据的事项分开。
3. 资料不完整但用户希望先出方案时，先形成一版尽可能完整的候选稿，同时标明事实、推断和待确认项，方便用户拿给专家校准。
4. 收到专家反馈后，更新相关术语、决定、假设和项目知识，并检查其他方案、PRD、原型和汇报是否受到影响。

缺少项目证据时，不用通用概念把空白填满。可以先说明目前理解到哪一步，再给出候选内容和需要校准的地方。

## 避免过度加工

以下写法容易让内容失去真实感，应主动收住：

- 为了好看强行整理成“两件事、三个阶段、四个层次”等对称框架。
- 每段都先写“核心观点、页面结论、一句话主旨、真正的变化”。
- 高频使用“重新定义、全面升级、产品进阶、形成闭环、赋能”等抽象词。
- 把一段具体经历过早改写成方法论、金句或口号。
- 用户仍在摸索时，把暂时理解写成已经验证的成熟结论。
- 用同一个固定句式包装所有判断，包括机械地把某个禁用句式替换成“核心是……”。

结构服务于理解。没有必要的标题、总结句和方法标签可以直接删掉。

## 轻度整理示例

原始表达：

> 我刚接这个事情的时候，其实里面好几个东西我都不懂。我先把资料都放到 AI 里面，让它给我梳理。它写得很快，我那时候也挺相信的。后来第一次拿去评审，人家一问具体业务，我发现我其实判断不了它写得对不对。

推荐整理：

> 我刚接手这件事时，里面有不少内容我都不懂。我先把能拿到的资料交给 AI，让它帮我梳理。它写得很快，我当时也很相信它。第一次拿去评审，专家开始追问具体业务时，我才发现自己其实判断不了它写得对不对。

过度加工：

> 这段经历让我完成了从“使用 AI”到“驾驭 AI”的认知跃迁，也验证了人机协同必须建立专业判断闭环。

后一种写法可以在事实充分、用户确实认同这个判断时作为后续提炼，不能替代事情本身。

## 交付前自检

- 这段话像用户本人会说的话吗？
- 读者能否先看到具体事情，再看到总结出来的观点？
- 是否保留了必要的不确定、限制、失败和转折？
- 重要判断能否回到项目资料、具体场景或明确推断？
- 能否删掉三分之一的标题、标签或总结句，意思仍然更清楚？
- 是否出现了用户没有说过、材料也无法证明的“漂亮结论”？

任一项不满足时，先回到事实和原话重新整理。
